# Move to UTR-based Automatic Payment Verification

This plan outlines the steps to transition the payment verification system from the current decimal-based matching trick to an automatic, UTR-based approach using Cloudflare Email Routing and Workers. This ensures 100% accurate matching for multiple simultaneous users without needing decimals.

## Proposed Changes

### 1. Update Order Generation API
#### [MODIFY] [route.js](file:///d:/Payment-Page/upi-payment-gateway/app/api/orders/route.js)
- **Remove Decimal Logic**: The current loop that increments the amount by `.01`, `.02` etc., will be completely removed. We will only insert the exact amount requested by the user.
- **Order ID Format**: Instead of a full UUID (which is 36 characters and might exceed the `tn` field limit of some UPI apps), we will generate a shorter, unique alphanumeric Order ID (e.g., `ORD-A1B2C3D4`). This ensures the ID fits reliably into the UPI note.

### 2. Update Frontend Payment Flow
#### [MODIFY] [page.jsx](file:///d:/Payment-Page/upi-payment-gateway/app/pay/page.jsx)
- **Use Order ID in Deep Link**: The `tn` parameter will safely contain the newly generated shorter Order ID. (This is mostly handled by the current `buildParams` implementation, but we'll ensure it works seamlessly with the new format).
- **Remove Dynamic Amount Display**: Remove any references to `dynamicAmount` so the exact requested amount is shown to the user.

### 3. Create Cloudflare Email Worker
#### [NEW] [worker.js](file:///d:/Payment-Page/upi-payment-gateway/cloudflare-worker/worker.js)
- Create the Cloudflare Worker script that will:
  1. Receive the IndusInd bank emails routed from Cloudflare.
  2. Parse the email body to extract the UTR, Amount, and the `tn` (Order ID) from the UPI string.
  3. Send a `PATCH` request to Supabase to mark the order as `paid`, filling in the `utr` and `paid_at` fields.

## Open Questions

> [!IMPORTANT]  
> **Order ID Length Limit**  
> Some UPI apps limit the transaction note (`tn`) length to 50 characters. A standard UUID is 36 characters, which is close but usually fits. To be completely safe and avoid cutoff in the bank's email, should we change the order IDs generated by the system to a shorter alphanumeric format like `ORD-ABC123`?

> [!WARNING]  
> **Supabase Table Schema**  
> We need to ensure that the Cloudflare Worker can update your Supabase `orders` table. Does the `orders` table have `utr` and `paid_at` (or `verified_at`) columns already set up to receive the data from the Worker?
